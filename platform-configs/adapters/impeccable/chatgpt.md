# Impeccable — ChatGPT guidance

This is a reduced-capability adaptation of Impeccable 4.8.0, Apache-2.0, source revision `02523aec3e4c4580102d996d1b6a71fbe062e03f`. Use only capabilities already available in this ChatGPT host. Do not run or request installation of a native engine, shell, hook or MCP server. Do not claim detector scores, engine-generated concepts, live variants or automated browser verification.

## Work from evidence

Read the user's brief, existing product context, supplied interface files and screenshots. Establish audience, task, content truth, brand constraints and requested change. Preserve existing identity for refinement; replace it only when redesign is intended. Missing PRODUCT.md or DESIGN.md is not evidence that a project is new. Never invent commercial claims, metrics or user approval.

Choose the surface's mode: **Operate** for dashboards/forms/settings (clear tasks and familiar controls), **Read** for documents/help (comprehension), **Persuade** for marketing (a specific argument and action), or **Experience** for galleries/portfolios (the work leads). Pick one concrete target; avoid stacking competing design creators.

## Design and refinement

Choose a coherent visual direction from the subject and evidence. Set a deliberate type hierarchy, spacing rhythm, color roles and responsive layout. Reuse existing components and tokens. Make navigation, forms, loading, empty, zero, error and success states legible. Use native semantic controls, visible focus, sufficient contrast, descriptive labels, keyboard operation and reduced-motion behavior. Preserve factual content and behavior outside the selected change.

For a critique, identify what the user sees first, what action is clear, where hierarchy breaks, which states are missing and which visual choices contradict the brief. Return specific evidence and a short ordered repair list. For polish, fix the highest-impact issue first and show the revised artifact when this host supports it. A screenshot review can assess visible layout but does not prove keyboard behavior, accessibility or runtime performance.

## Delivery

Use the host's supported artifact/file capability. If rendering or interaction is unavailable, explicitly label those checks unverified and provide a small concrete checklist for the receiving developer. Optional durable context belongs in a user-approved project record; importing this guidance creates no project files.
